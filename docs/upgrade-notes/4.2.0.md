Upgrade from 4.1.1 while the roof is idle. Keep a full private backup or VM snapshot, the installation record,
identity data, settings, certificates, device keys and previous-version assets. 4.1.2 was never released; its
deployment-availability guidance is included below.

The installed 4.1.1 installer rejects this release's identity schema 3 before replacing itself or displaying these
notes (`identityStoreSchema must be 1 or 2`). Use the published 4.2.0 release's bootstrap script, which verifies
the installer it downloads, instead of the installed `hvo-roof-install upgrade`:

```bash
version='4.2.0'
curl -fsSL --proto '=https' --tlsv1.2 -o install.sh \
  "https://github.com/HualapaiValley/HVO.RoofController/releases/download/v${version}/install.sh"
bash install.sh upgrade --version "$version"
```

Run this only once 4.2.0 is published. The bootstrap uses sudo for recorded system roles; upgrade separately
installed per-user CLI and Mac clients as their user, without sudo. For an offline release folder, run that
release's script with `bash install.sh --from /path/to/release upgrade --version "$version"`. The bootstrap
checks the downloaded installer's SHA-256 and, when authenticated `gh` is available, its attestation.

Existing users, native enrollments, keys and configuration are retained. Existing installations gain no temporary
default PIN; Choose/Confirm commissioning is for a clean first installation. Do not uninstall, delete identity
files, re-enroll users or edit `identityStoreSchema` to bypass the old installer's rejection. The new installer
backs up the stores before changing the installation. A schema-2 store permits compatible rollback; if the store
has moved to schema 3, returning to 4.1.1 requires `rollback --restore-backup`, restoring the upgrade backup and
losing identity changes made since it. Preserve that backup. A plain incompatible rollback is refused.

Before upgrading a controller or Linux rig, ensure Docker can enforce CPU, memory, swap and process limits;
unsupported hosts are refused before changes, with no override. On stock Raspberry Pi OS, append
` cgroup_enable=memory` to the existing single line in `/boot/firmware/cmdline.txt` and reboot with the roof idle
before upgrading. The default controller limits are now 1 vCPU, 2 GiB with no swap, and 512 processes, including
when upgrading a previously unlimited container. Retained or explicit limits must provide at least 1 vCPU and
1 GiB; no unlimited setting remains. Compose also requires verifiable cgroup v2 limits. Preserve configured limits
for upgrade and rollback. The mounted secrets, certificate, identity and settings directories must be root-owned
as described in the deployment guide; the container no longer has `CAP_DAC_OVERRIDE`.

Deploys now retain a safely stopped controller with a classified drive or limit fault (including an unpowered
drive), with a warning naming the fault. Inspect the cause and settings, particularly a fault first seen after
upgrading; restore the plant and explicitly `ClearFault` before commanding motion. Faults are never cleared
automatically. `/health` and `/health/ready` still fail for plant latches; Docker uses `/health/available` for
software and I/O availability. Older images without that endpoint still use strict readiness, including during
rollback, so a plant fault can still fail their verification. This availability fix requires no manual setting,
account or identity-store change of its own.

Upgrade the controller and all clients for the shared HVO Dark redesign. Kiosk PIN access remains Operator-only;
use web, CLI/TUI or a password-authenticated Mac session for administration. The kiosk's Terminal exit requires
an operator PIN and confirmation, then exposes an ordinary Linux login; returning locks the kiosk again.
The bootstrap does not change certificate trust or bypass browser warnings. Local candidate testing does not
establish published-download, attestation-service or interactive kiosk/browser acceptance.
